## Security, Trust and On-Chain Verification (Phase 2)

### The Aim for This Week

Last week I tackled priority 1 and 2 of the comments on my issue which was the vote signature verification problem and CKB transaction verification problem. This week the aim is to finish up the remaining two priorities:

- Transition reward amounts from floating point CKB amounts to integers shannons in order to avoid precision bugs with money storage

- Finally I responded to the comments on the contestLedger issue

### What I Learned

- Learnt that the Migration threshold does matter
  Migration threshold for the migration was set at 1,000,000,000 that is the line where CKB values turn into shannon values.
  As the minimum reward equals 100 CKB, which is equal to 10,000,000,000 shannons, the threshold is safe enough for separation of old and new data.
  It allows avoiding unnecessary changes in newly stored data during the migration.

- The Display vs The Storage
  Shannons are stored in a consistent way, but the conversion of values to CKB takes place only while displaying them.
  Using the single `shannonsToCkb()` function allows to keep the logic of conversion of values in one place.

- Outpoints make relationships native to chain
  Foreign key of a database can guarantee the existence of the relationship only inside the database itself.
  However, on-chain outpoint ensures that the contest-entry relationship is verifiable on CKB.
