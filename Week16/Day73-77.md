# Day 73-77: Aug 3rd - Aug 7th, 2026

## Security and On-Chain Verification 

### Overview
Last month I delivered the working version of ContestLedger with features like wallet connect, contest creation section, entry submission and voting powered by fiber all linked to real CKB transactions on Pudge testnet. The project was reviewed and several security and integrity issues was pointed out that needed to be addressed before the project could be taken seriously as a decentralized application.

This week was about looking into those issues and fixing them properly.

### What I Was Asked to Fix
- Priority 1 - Wallet Signature Verification for Votes: So basically, the votes API accepted any wallet address passed from the frontend and blindly trusted that address. Anyone could POST an address that doesn't exist to the API and cast as many votes as they like from any wallet address they don't own.

- Priority 2 - Verify CKB TX When Indexing: While creating contests and entries, the frontend pushed data straight into the database without the backend even checking the actual CKB transaction. A forged TX hash and some garbage would be considered as the truth. 

- Priority 3 - Use Shannons instead of CKB Floats: The amounts of reward were kept in floats and in units of CKB causing the money precision problem since there is one. Shannons are CKB's native unit (1 CKB = 100,000,000 shannons).

- Priority 4 - Contest/Entry Relation by On-Chain Outpoints: The entries referred to contests by the database ID and not by their on-chain outpoint, wgich means that the relationship between them was not on-chain verifiable.
