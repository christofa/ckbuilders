# Day 73-77: Aug 3rd - Aug 7th, 2026

## Security, Trust and On-Chain Verification 

### Overview
Last month I delivered the working version of ContestLedger with features like wallet connect, contest creation section, entry submission, and voting powered by fiber, all linked to real CKB transactions on Pudge testnet. The project was reviewed, and several security and integrity issues were pointed out that needed to be addressed before the project could be taken seriously as a decentralized application.

This week was about looking into those issues and fixing them properly.

### What I Was Asked to Fix
- Priority 1 - Wallet Signature Verification for Votes: So basically, the votes API accepted any wallet address passed from the frontend and blindly trusted that address. Anyone could POST an address that doesn't exist to the API and cast as many votes as they like from any wallet address they don't own.

- Priority 2 - Verify CKB TX When Indexing: While creating contests and entries, the frontend pushed data straight into the database without the backend even checking the actual CKB transaction. A forged TX hash and some garbage would be considered the truth. 

- Priority 3 - Use Shannons instead of CKB Floats: The amounts of reward were kept in floats and in units of CKB, causing the money precision problem since there is one. Shannons are CKB's native unit (1 CKB = 100,000,000 shannons).

- Priority 4 - Contest/Entry Relation by On-Chain Outpoints: The entries referred to contests by the database ID and not by their on-chain outpoint, which means that the relationship between them was not on-chain verifiable.

This week I worked on Priorities 1 and 2

### Goal for the Week
- Make ContestLedger truly trustworthy
- Votes should have proof that they came from the wallet claimed
- Contests and entries should be validated using CKB transactions before entering the database
- No data goes to Turso unless it has been validated on-chain first


### What I Learned
- The package boundaries of server and client in Next.js become especially relevant when working with blockchain SDKs. There is a specific reason why CCC keeps its connector and core library separated into distinct packages. API routes should be server-side only and thus can only rely on safe server-side packages.
- Decentralization does not equal trustworthiness. Writing to a blockchain and writing to the database are two different operations. Unless there is a verification step between them, the database is just another web app that broadcasts transactions to a blockchain. Decentralization means that the database only recognizes data written to the blockchain.
- Read the source before assuming field names. The Cell data field name issue was entirely avoidable. If I had checked what the frontend actually encoded before writing the verification logic, it would have been creator from the start. Assumptions about naming conventions cost debugging time.
